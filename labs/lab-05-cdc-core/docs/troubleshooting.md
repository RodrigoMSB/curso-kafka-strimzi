# Troubleshooting — Lab 05

| # | Problema | Causa típica | Solución |
|---|----------|--------------|----------|
| 1 | El build de Connect falla al empujar la imagen ("connection refused" / "push" error). | **El error más probable**: el registry local no está corriendo o no está conectado a la red de kind. | Ejecuta `bin/01-registry-local.sh` (idempotente). Verifica `docker ps | grep kind-registry` y que esté en la red kind (`docker network inspect kind`). |
| 2 | El build "no termina": ¿lento o colgado? | El build descarga la base de Connect + el plugin (minutos la primera vez). | Mira los logs: `kubectl logs -f connect-cdc-connect-build -n meridiano-pagos`. Si avanza (descargando/construyendo), es lento, espera. Si el pod está en error/CrashLoop o sin logs nuevos por mucho rato, está colgado: revisa la fila 1 (registry) y la red. |
| 3 | El conector queda `FAILED`. | Error de conexión a la BD, credenciales, o un permiso de PostgreSQL. | Lee el status: `kubectl get kafkaconnector core-clientes -n meridiano-pagos -o jsonpath='{.status.connectorStatus.tasks[*].trace}'`. Y los logs del pod de Connect. La traza indica la causa exacta. |
| 4 | El conector no arranca: "logical decoding requires wal_level >= logical". | PostgreSQL no tiene `wal_level=logical`. | El Deployment del core debe arrancar con `-c wal_level=logical` (ver `infra/core/30-postgres.yaml`). Confirma: `kubectl exec -n meridiano-core deploy/core-postgres -- psql -U postgres -tAc "SHOW wal_level"`. |
| 5 | Los UPDATE/DELETE no traen `before` completo (solo la clave). | La tabla está en `REPLICA IDENTITY DEFAULT`. | Pon `ALTER TABLE clientes REPLICA IDENTITY FULL;` (el init lo hace). Confirma con `\d+ clientes` (Replica Identity: full). |
| 5b | El conector falla con "publication does not exist" o un error de permisos al crear la publicación. | El usuario `debezium` no es superusuario y la publicación no existe. | La publicación se crea en el init como superusuario (`CREATE PUBLICATION dbz_publication FOR ALL TABLES`). El conector la usa con `publication.autocreate.mode: disabled`. Verifica `SELECT * FROM pg_publication;`. |
| 6 | Connect arranca pero el conector falla con un error de autorización de Kafka (ACL). | Falta una ACL en el KafkaUser `connect-cdc`. | El síntoma es un `TopicAuthorization\|GroupAuthorization\|ClusterAuthorization` en la traza del task. Revisa que `connect-cdc` tenga las ACLs de prefijo (`connect-cdc` para internos y grupo, `core.` para destino) e `IdempotentWrite` de cluster. |
| 7 | El tópico `core.public.clientes` no nace. | El conector no llegó a hacer snapshot/streaming (FAILED), o no hay cambios. | Confirma el conector `RUNNING` (fila 3). El tópico nace con el primer evento (snapshot incluido). Lista con `kubectl get kafkatopics -n meridiano-pagos | grep core`. |
| 8 | Tras "caer" el core (scale 0) el conector no se recupera al volver. | El conector reintenta con backoff; puede tardar. | Espera a que el core esté Ready (`kubectl rollout status deployment/core-postgres -n meridiano-core`) y vuelve a mirar el estado de la tarea; debería volver a `RUNNING`. Si quedó `FAILED` de forma permanente, reinicia el conector (re-aplica o usa la anotación de restart). |
