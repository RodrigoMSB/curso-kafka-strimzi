# Troubleshooting — Capstone "La migración"

| Síntoma | Causa probable | Solución |
|---|---|---|
| **MM2 queda `NotReady` o no replica nada** (el fallo más probable) | ACLs insuficientes de la **identidad del target**. En el destino MM2 debe **crear y escribir** el tópico replicado y sus tópicos internos de Connect; con `authorization: simple`, sin esas ACLs el connector falla silenciosamente. | Da a `mm2-migracion` ACLs de `Create/Write/Describe/Read/AlterConfigs` sobre `topic "*"`, `Read/Describe` sobre `group "*"` y operación de `cluster`. Revisa los logs del pod `migracion-legado-a-pagos-mirrormaker2-*` (`Authorization` denegada). |
| **El legado es inalcanzable desde los pods** | El contenedor no está en la red de kind, o `advertised.listeners` apunta a `localhost`. | El contenedor debe estar en la red `kind` (`docker network`), y advertir su **nombre** (`kafka-legado:9092`), no `localhost`: el cliente, tras el bootstrap, conecta a la dirección advertida y el pod debe poder resolverla. (Precedente: el registry del Lab 05.) |
| **El broker legado no arranca** (`Could not create the JVM`, `-Xlog gc.log`) | La imagen del curso intenta escribir el GC log en `/opt/kafka/logs`, no escribible. | Arranca el contenedor con `LOG_DIR=/tmp/logs` (lo hace `01-desplegar-legado.sh`). |
| **Los conteos no calzan** | Consumir un tópico **vivo** con `--timeout-ms` no termina (llega 1 msg/s). | Cuenta con los **offsets finales** (`kafka-get-offsets.sh ... --time -1`, sumando particiones) y, para inspeccionar la serie, consume con `--max-messages <total>` (snapshot determinista). Recuerda autenticar (el destino es SCRAM). |
| **El consumidor de conteo da 0 o error de auth** | Falta `--consumer.config`/`--command-config` con las credenciales SCRAM, o el usuario no tiene `Read` sobre el tópico. | Usa una identidad con `Read` (p. ej. `mm2-migracion`). `app-pagos` **no** sirve: su ACL es para otro tópico. |
| **Hueco en la serie tras el cutover** | El productor nuevo arrancó en un ID que no es último+1, o se apagó el legado **antes** de que MM2 drenara toda su historia. | El primer ID nuevo debe ser `último-del-legado + 1` (lo registra `02-cutover`). Antes de decomisar, confirma que `max(origen=legado)` en el destino == último ID del legado. |
| **Duplicado en la serie tras el cutover** | El legado siguió emitiendo tras leer el "último ID", o el productor nuevo arrancó por debajo de la frontera. | `02-cutover` detiene el productor del legado (archivo de parada) **antes** de leer el último ID y arranca el nuevo en último+1. No reactives el legado tras el cutover. |
| **`03-decomisar-legado.sh` se niega a apagar** | Salvaguarda anti-decomiso-prematuro: no consta el cutover (`migracion-estado.ultimo-id-legado` vacío). | Ejecuta primero `02-cutover`. Si de verdad quieres forzarlo, `--forzar` (bajo tu responsabilidad). |
| **El tópico destino quedó con RF=1** | Se dejó que MM2 lo autocreara con la durabilidad del origen, o el KafkaTopic declaró `replicas: 1`. | Declara `legado.transferencias` como **KafkaTopic con `replicas: 3`** antes de levantar MM2 (hereda la durabilidad de la plataforma). |
| **El 90 falla en "Plataforma intacta"** | La migración rompió algo del Lab 07 (p. ej. se tocaron listeners/authorization de `pagos`). | No endurezcas/debilites `pagos` para "que funcione". El destino ya está bien; ajusta las **ACLs del usuario**, no el clúster. Recupera el Lab 07 si hace falta. |
