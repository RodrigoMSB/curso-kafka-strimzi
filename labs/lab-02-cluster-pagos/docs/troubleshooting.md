# Troubleshooting — Lab 02

| # | Problema | Causa típica | Solución |
|---|----------|--------------|----------|
| 1 | Pods de broker/controller en `Pending`. | Docker no tiene CPU/memoria suficientes para 4 nodos + Kafka. | Sube los recursos de Docker Desktop (Settings → Resources; recomendado 8+ GB y 4+ CPU). Revisa el motivo con `kubectl describe pod <pod> -n meridiano-pagos` (sección Events). |
| 2 | Los pods quedan mucho tiempo en `ContainerCreating`. | La imagen de Kafka (~cientos de MB) se está descargando la primera vez en cada nodo. | Espera; en redes corporativas/VPN puede tardar. Mira el avance con `kubectl describe pod <pod> -n meridiano-pagos`. |
| 3 | `kubectl get kafka pagos` muestra `READY` vacío o el CR no llega a Ready. | El clúster aún converge, o hay un problema de configuración. | Lee las condiciones: `kubectl get kafka pagos -n meridiano-pagos -o yaml` y busca `status.conditions` (campos `type`, `status`, `reason`, `message`). El `message` suele indicar la causa. Revisa también los logs del operador. |
| 4 | El pod cliente no conecta: "no resolvable" o timeouts contra el bootstrap. | Nombre o namespace del bootstrap equivocado, o el clúster no está Ready. | Usa `pagos-kafka-bootstrap:9092` y ejecuta el pod cliente en `-n meridiano-pagos`. Confirma el servicio con `kubectl get svc -n meridiano-pagos | grep bootstrap`. |
| 5 | El PVC de un broker queda en `Pending`. | No hay StorageClass por defecto o no puede aprovisionar el volumen. | Verifica la StorageClass: `kubectl get storageclass` (en kind debe existir `standard` como `(default)`). Revisa el PVC con `kubectl describe pvc <pvc> -n meridiano-pagos`. |
| 6 | Cambiaste el `type` del storage de un pool y el cambio "no toma". | El tipo de storage **no es modificable en caliente**: se decide al crear el pool. | Es el comportamiento esperado (ver guía 04). El operador deja una condición `Warning` con `reason: KafkaStorage` y el mensaje "...contains changes which are not allowed. As a result, all storage changes will be ignored." El clúster sigue `Ready`. Para cambiarlo de verdad, recrea los recursos: borra el `Kafka` y los `KafkaNodePool` y vuelve a aplicarlos con el storage deseado. |
| 7 | El rolling update no termina (un broker no vuelve a `Running`). | Recursos insuficientes para reprogramar el pod, o el pod nuevo no pasa readiness. | Mira qué pod está atascado (`kubectl get pods -n meridiano-pagos`) y por qué (`kubectl describe pod <pod>`). Suele ser memoria/CPU de Docker (fila 1) o una imagen aún descargándose (fila 2). |
